# Схема геймплейных данных (`data/*.json`)

> **Придумываете вызов, а не читаете схему?** Начните с `docs/КАК-ДЕЛАТЬ-МИССИИ.md` —
> там про то, как выбирать пороги и варианты, и про инструмент, который заводит все файлы сам.

> **Не путать со схемой текстов.** Проза живёт в `content/raw/**/*.md` и собирается
> конвертером в `content/localisation/`; её схема — `content/raw/_system/Syntax/README.md`.
> Здесь описано только то, что крутит дизайнер числами, и ссылки на тексты по id.


Схему задаёт ядро. Текстовый движок (Obsidian `.md` → JSON, раздел 14 ДД) обязан
выдавать ровно этот формат. Это закрывает открытый вопрос про фронтматтер:
конвертеру не нужно «угадывать» тип записи — он собирает файлы по типам.

Общие правила:

* имена полей — camelCase, регистр при чтении не важен;
* перечисления пишутся строками (`"Consumable"`, `"Infected"`, `"AgainstCreatureTag"`);
* пропущенное поле = значение по умолчанию, `null` для необязательных ссылок;
* блок характеристик — объект с любым подмножеством из пяти ключей:
  `strength`, `perception`, `endurance`, `agility`, `composure`;
* блок изменения шкал — объект с любым подмножеством: `infection`, `publicity`, `loyalty`
  (положительное = рост шкалы; для лояльности рост — это хорошо, для остальных — плохо);
* комментарии `//` и висящие запятые допускаются.

Загрузчик **валидирует ссылочную целостность** и падает с понятным сообщением,
если миссия ссылается на несуществующую зону, существо, свойство или радио-сцену.
Это специально: битую ссылку нужно ловить на загрузке, а не на середине смены.

---

## `config.json` — один объект

Все балансные числа. Разделы: `timings`, `scales`, `resolution`, `employees`,
`zones`, `loot`, `days[]`. Полный список полей — в `src/Kontur.Core/Config/SimulationConfig.cs`
(там же значения по умолчанию и ссылки на пункты ДД).

Ключевое: числа из ДД (15 / 30 / 20 секунд, окно 300 с, лимиты штата 3/4/5/6,
5–10 вызовов) живут здесь, а не в коде.

### Сценарные и обучающие смены

У каждого дня в `days[]` есть три необязательных поля, позволяющих превратить смену
в обучающую, не трогая код (ДД, раздел 12: сложность задаётся контентом и параметрами):

```json
{
  "day": 1,
  "disableTimers": true,
  "sequentialCallCount": 3,
  "missionOrder": ["m_d1_02", "m_d1_05", "m_d1_03", "m_d1_06", "m_d1_04"]
}
```

| Поле | Что делает |
|---|---|
| `disableTimers` | Отключает таймеры игрока: звонок, метка и радио ждут действия сколько угодно. Таймеры дороги, работы на объекте и возвращения продолжают идти — иначе вызов не завершится. В событиях `IncidentCreated`, `MapMarkerSpawned`, `RadioTriggered` длительность приходит равной `0` — интерфейс по этому признаку не рисует обратный отсчёт. |
| `sequentialCallCount` | Сколько первых вызовов приходят строго по одному: следующий не поступит, пока не закрыт предыдущий. Остальные идут обычным расписанием, поэтому конец смены можно сделать с наложением. |
| `missionOrder` | Жёсткий порядок миссий вместо случайного подбора. `minCalls`/`maxCalls` при этом игнорируются, а неизвестный Id — ошибка загрузки, а не тихий пропуск. Сценарная смена завершается сразу после закрытия последнего вызова, не дожидаясь конца пятиминутного окна. |

День 1 в поставляемом контенте использует все три: сначала простой вызов с раскрытием
энциклопедии, затем два вызова с радио, в конце два внахлёст.

## `zones.json` — массив

```json
{ "id": "z_center", "name": "Центральный район", "state": "Normal",
  "baseWeight": 1.0, "mapX": 0.50, "mapY": 0.45 }
```

`state`: `Normal` | `Infected` | `Quarantine` | `Cleared`.
`mapX`/`mapY` — нормализованные координаты для отрисовки метки; ядру не нужны,
прокидываются в UI как есть.

## `buildings.json` — массив, необязателен

```json
[
  { "id": "building_block_r01_c02", "isDispatchTarget": true },
  { "id": "building_block_r04_c03", "isHeadquarters": true },
  { "id": "building_block_r02_c05", "isDispatchTarget": true, "zoneId": "z_center" }
]
```

Дома, нарисованные на карте. Отвечают на вопрос «в какой подъезд едет группа»,
тогда как зона отвечает на «насколько там паршиво». Файл генерируется инструментом
`tools/map-geometry-generator` вместе с геометрией карты.

| Поле | Смысл |
|---|---|
| `isDispatchTarget` | сюда можно отправить группу |
| `isHeadquarters` | главное управление; отсюда выезжают и сюда возвращаются |
| `zoneId` | район дома; **необязателен**, см. ниже |

**Дом выбирается на каждую смену заново** и живёт на инциденте, а не на миссии:
один и тот же вызов дважды не должен приходить из одного подъезда. Два вызова
за смену в один дом тоже не попадут — две метки на одном здании игрок прочитал бы
как ошибку отрисовки.

**`zoneId` пока не проставлен ни у одного дома, и это работает.** Если у домов есть
районы, планировщик выбирает только среди домов нужного района. Если нет — берёт любой
свободный: пустая карта хуже неточной. Как только районы появятся, метки начнут
попадать в нужную часть города сами, без правок кода.

**Файла может не быть вовсе.** Тогда `BuildingId` в событиях приходит пустым, и метку
надо ставить по координатам зоны. Ветку с зоной интерфейсу стоит написать в любом
случае — она же работает в отладочных прогонах без карты.

Проверяется при загрузке: неизвестный `zoneId`, повторяющийся `id`, отсутствие целей
отправки, больше одного главного управления и здание, помеченное разом как штаб
и как цель отправки — группа получила бы вызов в собственную контору.

## `creatures.json` — массив

```json
{
  "id": "creature_mimic",
  "tags": ["мимик"],
  "illustrationId": "art_mimic",
  "properties": ["property_mimic_routine", "property_mimic_speech", "property_mimic_break"]
}
```

Ни имени, ни абзацев: всё это в статье `content/raw/creatures/*.md` под тем же `id`.
`properties` — только идентификаторы скрытых свойств; каждому в тексте соответствует
блок `%% reveal: <id> %%`. Загрузчик сверяет одно с другим через каталог текстов
и падает на расхождении.

`tags` — для условий перков («мимик», «перекожник»), они геймплейные и остаются здесь.

## `abilities.json` — массив

```json
{ "id": "ab_mimic_hunter",
  "condition": "AgainstCreatureTag", "conditionValue": "мимик", "allStatsBonus": 1 }
```

`condition`: `Always` | `AgainstCreatureTag` | `WithEquipment`.
`conditionValue` — тег существа или id снаряжения.
`bonus` — точечные прибавки, `allStatsBonus` — ко всем сразу. Можно вместе.

Названия и описания перков здесь не хранятся: они лежат в текстовом движке
(`content/raw/UI/perks`) и достаются по тому же `id`. Ядро отдаёт наружу
`EmployeeView.AbilityIds`, названия резолвит слой Godot. Числа в описании
подставляются из полей отсюда тегом `{{bonus.strength}}`, так что правка
баланса не требует правки текста.

## `equipment.json` — массив

```json
{ "id": "eq_armor", "name": "Бронежилет 6Б", "kind": "Standard",
  "bonus": { "endurance": 3 }, "deathChanceMultiplier": 0.5 }
```

`kind`: `Consumable` (тратится всегда) | `Standard` (возвращается после успеха) |
`Story` (теряется только при гибели всей группы).
`successChanceBonus` — прямая прибавка к шансу при броске, `0..1`.

## `employees.json` — один объект

```json
{
  "startingRoster": [ { "id": "emp_gorin", "name": "Горин А. П.", "level": 2,
                        "stats": { "strength": 5 }, "abilities": ["ab_skin_breaker"] } ],
  "hirePool":      [ { "id": "emp_shubin", "availableFromDay": 2, "...": "..." } ]
}
```

`availableFromDay` реализует правило ДД «на поздних сменах нанимаемые сотрудники
стартуют с более высокими базовыми характеристиками» — просто кладите сильных
кандидатов с бо́льшим значением.

### `generator` — фабрика кандидатов

Прописанные вручную кандидаты конечны, а смен много. Фабрика добирает список найма
до `candidatesPerShift`; сюжетные лица из `hirePool` всегда идут первыми и вытесняют
сгенерированных, а не наоборот.

```json
"generator": {
  "candidatesPerShift": 3,

  "minStat": 2,
  "maxStat": 7,
  "statPointsBase": 8,
  "statPointsPerLevel": 4,
  "primaryWeight": 3,
  "secondaryWeight": 2,

  "abilitiesBase": 1,
  "secondAbilityFromLevel": 3,

  "startingChoicePoolSize": 6,

  "levelsByDay": [
    { "fromDay": 1, "minLevel": 1, "maxLevel": 1 },
    { "fromDay": 4, "minLevel": 2, "maxLevel": 3 }
  ],

  "surnames": ["Аникеев", "Балуев", "..."],
  "initials": ["А. В.", "Б. Н.", "..."],
  "portraits": ["port_generic_1", "..."],

  "archetypes": [
    {
      "id": "arch_muscle",
      "weight": 3,
      "rankTitle": "оперативник",
      "primary": ["strength", "endurance"],
      "secondary": ["composure"],
      "abilities": ["ab_skin_breaker", "ab_calm"],
      "portraits": []
    }
  ]
}
```

**Бюджет и архетип — две разные ручки, и это нарочно.** Бюджет отвечает за то,
насколько кандидат силён вообще, и растёт по дням вместе со сложностью. Архетип — за то,
куда эта сила вложена. Правятся по отдельности, балансировать так заметно проще.

**Как считаются характеристики.** Все пять начинают с `minStat`. Сверх этого
раздаётся бюджет `statPointsBase + statPointsPerLevel × (уровень − 1)` — по одному
очку за раз, случайной характеристике. Основные архетипа тянут очко в `primaryWeight`
раз чаще, второстепенные — в `secondaryWeight`, прочие весят 1.

Вес задаётся **на характеристику, а не долей на пул** — и это не косметика. При долях
архетип с двумя основными и одной второстепенной получал бы самой высокой именно
второстепенную: её доля ни с кем не делится, а доля основных делится надвое. Силуэт
выходил бы обратный задуманному, и заметить это на глаз почти невозможно.

Упёршаяся в `maxStat` характеристика просто выбывает из розыгрыша, и очко достаётся
другой, а не пропадает. Поэтому сумма характеристик кандидата всегда ровно
`minStat × 5 + бюджет` — на этом держится проверка в `--selftest`.

Ориентир при `primaryWeight: 3`, `secondaryWeight: 2`, бюджете 22 очка (уровень 2):
основные выходят в среднем около 5,5, второстепенные — около 4,5, прочие — около 3,2.

**Перки берутся только из пула архетипа.** Придумать перк на лету нельзя: у него есть
и текст, и игровой эффект. Разнообразие даёт сочетание, а не новые способности.
Кандидат получает `abilitiesBase` перков, а с уровня `secondAbilityFromLevel` — на один
больше. Пул меньше нужного — выдаётся сколько есть.

**Отключается нулём.** `candidatesPerShift: 0` — фабрика молчит, предлагаются только
кандидаты из `hirePool`.

**`startingChoicePoolSize` — стартовый выбор состава.** Сколько кандидатов показать
перед первой сменой, чтобы игрок собрал из них бригаду. Должен быть больше лимита
штата первого дня: смысл выбора в том, чтобы от кого-то отказаться. Ноль отключает
экран — штат тогда берётся из `startingRoster` как есть, и игра начинается сразу
с первой смены.

**Что проверяется при загрузке:** неизвестная характеристика в `primary`/`secondary`,
неизвестный перк, `weight ≤ 0` (архетип никогда не выпадет), `maxStat < minStat`,
`minLevel > maxLevel` и — главное — бюджет, который не помещается в пять характеристик.
Последнее иначе выглядело бы не как ошибка, а как «кандидаты почему-то слабоваты».

**Портреты ядро не проверяет** — это чистые id для интерфейса. `port_generic_*`
в текущем контенте нарисованы не все.

## `mission_events.json` — массив

```json
{
  "id": "mission_event_pensioner_door",
  "options": {
    "pass_by":   { "revealsPropertyId": "property_mimic_routine",
                   "consequenceCap": "Injury",
                   "extraScales": { "publicity": -1 } },
    "capture":   { "deathChanceMultiplier": 2.2, "injuryChanceMultiplier": 1.6,
                   "extraScales": { "publicity": 4, "loyalty": -2 } },
    "left_turn": { "appliesQuarantine": false, "injuryChanceMultiplier": 1.2 }
  }
}
```

Только баланс. Формулировки вариантов, `requirement_modifier` и `canon` лежат в
`content/raw/mission_events/*.md` под тем же `id` — автор правит их вместе с текстом.

**Ключи `options` обязаны совпадать с `id` вариантов в тексте.** Вариант без баланса
молча получил бы нейтральные риски, баланс без текста не показался бы игроку — поэтому
расхождение это ошибка загрузки, а не предупреждение.

`consequenceCap` у варианта **только ужесточает** потолок миссии. Тихо переждать
в кладовке безопасно везде, но никакой выбор не сделает смертельным вызов, который
дизайнер объявил безопасным — попытка ослабить потолок это ошибка загрузки.

Порядок вариантов задаёт текст: игрок видит их в порядке файла `.md`.


## `missions.json` — массив

```json
{
  "id": "m_pensioner_door",
  "day": 1,
  "zoneId": "z_sleep",
  "creatureId": "creature_mimic",
  "callId": "call_pensioner_door",
  "missionEventId": "mission_event_pensioner_door",
  "requirements": { "perception": 7, "agility": 5 },
  "travelSeconds": 12, "onSiteSeconds": 6, "returnSeconds": 10,
  "scalesOnSuccess":       { "infection": -2, "publicity": -1, "loyalty":  2 },
  "scalesOnFailure":       { "infection":  5, "publicity":  4, "loyalty": -4 },
  "scalesOnMissedCall":    { "infection":  6, "publicity":  6, "loyalty": -6 },
  "scalesOnExpiredMarker": { "infection":  5, "publicity":  5, "loyalty": -5 },
  "experienceOnSuccess": 100, "experienceOnFailure": 25,
  "injuryChance": 0.22, "deathChance": 0.06,
  "reports": {
    "":          { "success": "report_pensioner_door_plain_success",   "failure": "report_pensioner_door_plain_failure" },
    "pass_by":   { "success": "report_pensioner_door_pass_by_success", "failure": "report_pensioner_door_pass_by_failure" },
    "capture":   { "success": "report_pensioner_door_capture_success", "failure": "report_pensioner_door_capture_failure" },
    "left_turn": { "success": "report_pensioner_door_left_turn_success","failure": "report_pensioner_door_left_turn_failure" }
  },
  "manifestedPropertyIds": []
}
```

* `tier` — `Story` или `Filler`, **по умолчанию `Filler`**. Забытое поле не должно
  молча включать смерти, поэтому умолчание безопасное. Вмешательство по радио бывает
  только у `Story` — на филлере это ошибка загрузки.
* `consequenceCap` — `None` | `Injury` | `Death`, потолок последствий. Если не задан,
  берётся от уровня: `Story` → `Death`, `Filler` → `Injury`. Это **потолок, а не шанс**:
  числа `injuryChance` и `deathChance` остаются, потолок их обрезает уже после всех
  множителей варианта и снаряжения. Так «в детском саду не умирают» становится
  проверяемым правилом, а не договорённостью не писать туда лишнего.
* `callId` — обязателен: это то, что игрок услышит в трубке.
* `missionEventId` пуст или отсутствует → вмешательство этой миссией не предусмотрено
  (ДД, раздел 8: решает дизайн задания, а не случайность).
* `creatureId` **может быть пустым** — не за каждой аномалией стоит существо со статьёй
  (грибок, поле, изменённая геометрия). Тогда энциклопедия не трогается, а в отчёте
  существо не указывается.
* `reports` — ключ это `id` варианта решения, пустая строка это исход без вмешательства.
  Связка живёт здесь, а не во фронтматтере отчёта: сам отчёт по схеме текстового движка
  не знает ни о миссии, ни о варианте. Один и тот же id можно указать дважды — так
  сделано в `m_black_mold`, где «Уксус и ковры» служит и исходом без вмешательства.
* `requirements` — **пороги по отдельным характеристикам**, а не общая сложность.
  Сравниваются с лучшим в группе по каждой характеристике: порог «Восприятие 5» закрывает
  конкретный человек, а не сумма отряда. Ноль означает «характеристика на вызове не нужна».
  Задаются «как для базового дня»: множители дня и штриховки зоны, а также надбавку
  выбранного варианта ядро применит само.
* `primaryStat` — главная характеристика вызова, весит вдвое при расчёте процента.
  Обязана входить в `requirements`, иначе ошибка загрузки. Пусто — все пороги равнозначны.


## Записок и катсцен отдельным файлом нет

`shift_notes.json` и `radio.json` удалены. Записка сменщика и ролик после смены
описываются прямо в дне: `shiftNoteId` и `outroCutsceneId` в `config.json` — обычные
ссылки на записи типов `shift_note` и `cutscene`.

Так у дня один источник настройки вместо трёх, и связка видна там же, где лимит штата
и число вызовов.
