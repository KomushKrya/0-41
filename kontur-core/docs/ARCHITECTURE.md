# Архитектура ядра

## Один принцип

Ядро — детерминированный автомат. У него есть три входа и один выход:

```
                 команды игрока  ──┐
   контент (JSON) ────────────────►│
                 Tick(delta) ─────►│  KonturSimulation  ├──► поток событий (Event Bus)
                                   └────────────────────┘
```

Ничего другого. Нет чтения системного времени, нет обращения к файлам во время
смены, нет случайности вне `IRandomSource`. Из этого следует главное практическое
свойство: **один seed + одна последовательность команд = один и тот же прогон**,
на любой машине, с любым шагом Tick. Баг воспроизводится, а не «иногда падает».

## Слои

| Слой | Что делает | Что ему запрещено |
|---|---|---|
| `Model` | типы данных: `Employee`, `MissionDefinition`, `StatBlock`, `Zone`… | знать о правилах |
| `Content` | читает и валидирует JSON, собирает `ContentDatabase` | меняться во время игры |
| `Content.ITextCatalog` | порт в текстовый движок: сверка id и числа вариантов | отдавать ядру прозу |
| `Config` | все балансные числа | быть захардкоженным в коде |
| `Systems` | правила: `ShiftDirector`, `MissionResolver`, `ScalesSystem`, … | знать о UI |
| `Api` | `KonturSimulation` — фасад, команды и снимки состояния | пропускать мутации мимо команд |
| `Events` | шина и список сигналов | зависеть от систем |

Зависимости идут строго вниз: `Api → Systems → Content/Config → Model → Events/Simulation`.

## Event Bus

Основной паттерн проекта по ДД (раздел 13). Реализация — `Kontur.Core.Events.EventBus`:

* типизированная подписка `Subscribe<T>` и «слушать всё» `SubscribeAll` (лог, отладка);
* публикация из обработчика не рекурсивна — вложенные события уходят в очередь
  и разбираются последовательно (иначе цепочка «резолв → гибель → шкалы → game over»
  разворачивалась бы в стек и порядок событий зависел бы от глубины);
* подписка возвращает `IDisposable` — в Godot это `_ExitTree()` без утечек.

Сигналы — иммутабельные `record`. Подписчик не может испортить состояние ядра,
поменяв поле события.

## Конечный автомат вызова

Вызовы накладываются друг на друга (ДД, раздел 3, п. 13), поэтому фаза и таймер
живут на каждом инциденте (`IncidentRuntime`), а не глобально.

```
Scheduled
   │ время пришло
   ▼
Ringing (15 с) ──просрочка──► [автопровал: CallMissed] ──► Closed
   │ AnswerCall
   ▼
Briefing (без таймера, ждёт кнопку ОК)
   │ ConfirmBriefing
   ▼
MarkerActive (30 с) ──просрочка──► [автопровал: MarkerExpired] ──► Closed
   │ DispatchSquad
   ▼
Travelling (travelSeconds)
   ▼
   ├─ миссия без радио ──► OnSite (onSiteSeconds)
   └─ миссия с радио ───► RadioPending (20 с)
                              │ ChooseRadioOption ──► OnSite
                              └ просрочка: RadioMissed ──► OnSite (шанс × 0.5)
   ▼
[расчёт: MissionResolved → шкалы → зона → опыт → энциклопедия]
   ▼
Returning (returnSeconds) ──► отчёт на компьютере ──► Closed
   (если погибла вся группа — сразу Closed, существо не опознано)
```

Смена завершается, когда закрылось окно приёма (5 минут) **и** не осталось
незакрытых вызовов — ровно как в ДД, п. 14.

## Где проходит граница Event Bus

Вопрос, который возникает первым при чтении кода: почему системы ядра не подписаны
на шину, а вызываются напрямую из `ShiftDirector`? Это осознанное решение, и вот его
границы.

```
        команды (прямые вызовы, возвращают CommandResult)
  UI ─────────────────────────────────────────────────────►  KonturSimulation
                                                                    │
                                                                    │ прямые вызовы
                                                                    ▼
                                                              ShiftDirector
                                                                    │
                                                    ┌───────────────┼───────────────┐
                                                    ▼               ▼               ▼
                                            ScalesSystem   RosterSystem   EncyclopediaSystem …
                                                    │               │               │
  UI ◄──────────────────────────────────────────────┴───────────────┴───────────────┘
        события (Event Bus, только наружу)
```

**Наружу — всё через шину.** 34 типа сигналов, 35 точек публикации. Любое изменение
состояния объявляется. Слой Godot подписывается и никогда не опрашивает ядро в `_Process`.
Здесь Event Bus работает ровно так, как задумано в ДД.

**Внутрь — только команды.** UI не публикует события в ядро. Он вызывает команды,
каждая возвращает `CommandResult` с явной причиной отказа. Событие «я хочу отправить
группу» невозможно отклонить с объяснением — вызов метода можно.

**Внутри ядра — прямые вызовы.** Причина одна и она практическая. Разрешение вызова —
транзакция с обязательным порядком:

```
потери → снаряжение → шкалы (и проверка game over) → опыт → энциклопедия → отчёт
```

Если это раскидать по подписчикам `MissionResolved`, порядок станет функцией от порядка
подписки. Смерть сотрудника, посчитанная после начисления ему опыта, — это не гипотетический
баг, а типовой. И главное: детерминизм (один seed = один прогон) держится именно на
жёстком порядке. Он же держит отладку — сейчас цепочка видна в стектрейсе, а не
восстанавливается по логу событий.

**Что это стоит.** Добавление новой системы, реагирующей на итог миссии, требует правки
`ShiftDirector`. Это осознанная плата: пока систем десяток, явный список в одном месте
читается лучше, чем неявный граф подписок.

**Когда пересмотреть.** Если появятся реакции, которым порядок безразличен (достижения,
аналитика, сюжетные флаги, звук), их правильно вешать подписчиками на шину, а не добавлять
в оркестратор. Шина для этого уже готова — `SubscribeAll` и типизированный `Subscribe<T>`.

## Расчёт миссии

```
требования = requirements(миссия)
           × requirementMultiplier(день)      // прогрессия сложности, раздел 12
           × requirementMultiplier(радио-вариант)  // раздел 8

сумма_группы = Σ характеристики сотрудников (минус дебафф травмы)
             + Σ бонусы сработавших спецспособностей
             + бонусы снаряжения                // на группу целиком, раздел 6

покрытие = 1 − (Σ нехваток по характеристикам) / (Σ требований)

покрытие ≥ 1            → автоматический успех, броска нет
иначе                   → шанс = покрытие² (+ бонусы снаряжения), потолок 0.95, пол 0.02
радио просрочено        → шанс × 0.5
```

Излишек по одной характеристике **не** компенсирует нехватку по другой — иначе
«отправить всех на всё» становилось бы доминирующей стратегией, а требования
миссий перестали бы читаться игроком.

Риски травм и гибели растут при низком покрытии: `1 + (1 − покрытие) × 1.5`,
и режутся при успехе. Все коэффициенты — в `config.json`.

## Почему систем несколько, а не один God-класс

`ShiftDirector` оркестрирует, но не считает. Правило одного места изменения:

* шкалы меняет только `ScalesSystem` (он же единственный проверяет game over);
* энциклопедию — только `EncyclopediaSystem`;
* штат, опыт и уровни — только `RosterSystem`;
* исход миссии считает только `MissionResolver` (и он не имеет побочных эффектов —
  возвращает `MissionOutcome`, применяет его директор).

Это то, что позволит потом безболезненно менять баланс: правка формулы не может
случайно поменять последовательность фаз.

## Открытые места, помеченные в коде

* Фаза `Briefing` не имеет таймера — если игрок не нажмёт ОК, вызов висит вечно.
  В ДД таймера нет; если он появится, добавляется одной строкой в `ConfirmBriefing`.
* Каталог снаряжения (открытый вопрос ДД, раздел 16) — сейчас 7 предметов-заглушек.
* Сценарные смены (`missionOrder`, `sequentialCallCount`, `disableTimers`) — расширение
  сверх ДД, сделанное под обучение. Планировщик в такой смене не выбирает миссии сам,
  а идёт по списку; директор придерживает следующий вызов, пока не закрыт предыдущий.
* Сохранение/загрузка не реализованы: `GameState` намеренно сериализуем как
  простой объект, но контракт сейва не фиксировался.
