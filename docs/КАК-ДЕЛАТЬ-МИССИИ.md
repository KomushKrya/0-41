# Как делать миссии

Документ для того, кто придумывает вызовы: геймдизайнера и сценариста.
Программировать не нужно — всё делается тремя командами и правкой текстовых файлов.

Если нужен справочник по коду — это `docs/ЯДРО-API.md`. Если по разметке текстов —
`content/raw/_system/Syntax/README.md`. Здесь про то, **как придумать вызов и не сломать баланс**.

---

## 1. Из чего состоит миссия

Один вызов — это шесть-восемь файлов, связанных по id:

```
   data/missions.json          ← числа: пороги, риски, шкалы, тайминги
   data/mission_events.json    ← числа вариантов: риски и последствия
        │
        │  ссылаются по id
        ▼
   content/raw/calls/<имя>.md            ← что говорят в трубку
   content/raw/mission_events/<имя>.md   ← что видят на месте + варианты решения
   content/raw/reports/<имя>/*.md        ← отчёты: по одному на вариант × исход
```

Разделение простое: **всё, что пишется словами, — в `content/raw`. Всё, что крутится
числами, — в `data`.** Одно исключение: у вариантов решения тип, надбавка и требования
живут в тексте, потому что автор правит их вместе с формулировкой.

Руками эти файлы заводить не надо — есть инструмент.

---

## 2. Три команды

```bash
# Завести миссию целиком: задаст вопросы и создаст все файлы
python content/engine/tools/mission.py new

# Собрать тексты в JSON, который читает игра
python content/engine/converter/build.py --include-drafts

# Посмотреть, во что превратились пороги
python content/engine/tools/mission.py preview m_ваша_миссия

# Сверить всё со всем
python content/engine/tools/mission.py check
```

Порядок именно такой: завели → написали тексты → собрали → посмотрели → проверили.

`check` объясняет проблемы словами и отличает «текста нет» от «текст есть, но забыли
собрать». `preview` — главный инструмент балансировки, к нему вернёмся в разделе 4.

## 3. Пороги: главная и второстепенные характеристики

У вызова нет общей «сложности». Есть **пороги по отдельным характеристикам**:

```json
"requirements": { "charisma": 5, "intellect": 4 },
"primaryStat": "charisma"
```

Читается так: «тут нужна харизма пять и интеллект четыре, главное — харизма».

**Сначала решите, сколько человек берёт вызов.** Это поле `squadLimit`, и оно важнее
самих чисел:

```json
"squadLimit": 1,
"requirements": { "charisma": 4, "intellect": 3 },
"primaryStat": "charisma"
```

По умолчанию **один** — как в Dispatch, где на вызов обычно едет один герой, и лишь
отдельные допускают группу. Единица не случайно выбрана умолчанием: характеристики
отряда **складываются**, и на вызове без лимита выгодно было бы отправлять всех
свободных, отчего выбор состава исчез бы.

**Пороги считаются под лимит.** На вызов для одного порог должен закрывать специалист:
четыре-пять по главной характеристике. На вызов для двоих — только пара: семь-восемь.
Проверить себя проще всего командой `preview` — она покажет таблицу по всем составам,
которые влезают в лимит.

> **Сейчас во всех пятнадцати миссиях стоит `squadLimit: 2`.** Не потому, что так
> задумано, а потому что пороги в `data/missions.json` посчитаны под пару: одиночка
> берёт вызов на 27–52 %, пара — на 92–100 %. Единицу можно ставить только вместе со
> снижением порогов примерно вдвое. Это стоит перебалансировать; `check` теперь
> ругается на миссии, где автоуспех даёт **любая** пара.

**Главная характеристика весит вдвое.** Это ваш основной рычаг: не нужно задирать числа,
чтобы показать, что вызов «про разговор» — достаточно назначить харизму главной.
Главная обязана входить в пороги, иначе загрузка упадёт.

### Три ступени

| Ступень | Условие | Вклад в процент |
|---|---|---|
| Зелёная | превышение на 2 и больше | полный |
| Жёлтая | ровно дотянул или +1 | 0.8 |
| Красная | недобор | падает **втрое за каждое** недостающее очко |

Все зелёные — успех без броска. Иначе процент это взвешенное среднее вкладов, и по нему
бросается кубик. Красный не запрещает отправку: иногда игроку приходится ехать теми,
кто остался, — но шанс падает резко.

### Сколько ставить

Вот кто есть в игре. Ставьте пороги относительно этой таблицы, а не «на глаз»:

Характеристик пять: **Сила**, **Боевая подготовка**, **Ловкость**, **Харизма**,
**Интеллект**. В JSON они пишутся как `strength`, `combat`, `agility`, `charisma`,
`intellect`.

Стартовый штат (`data/employees.json`, раздел `startingRoster`):

| Кто | Сила | Бой | Ловк. | Хариз. | Интел. |
|---|---|---|---|---|---|
| Горин А. П. | 5 | 4 | 3 | 3 | 3 |
| Васнецова И. С. | 3 | 3 | 4 | 3 | 5 |
| Лядов М. М. | 4 | 4 | 3 | 4 | 3 |
| **Лучший в стартовом штате** | **5** | **4** | **4** | **4** | **5** |
| **Все трое вместе (сумма)** | **12** | **11** | **10** | **10** | **11** |

Дальше штат пополняется наймом, и там фиксированных людей нет: кандидатов собирает
фабрика по архетипам (`generator` в том же файле). Ориентиры, которые она даёт:

| Уровень кандидата | Главная характеристика | Слабейшая |
|---|---|---|
| 1 (день 1) | 5 | 2 |
| 2 (со дня 2) | 6–7 | 2–3 |
| 3 (со дня 4) | 7 | 3 |

То есть **на порог выше 7 не может выйти ни один одиночка** — потолок характеристики
(`maxStat`) равен семи. Всё, что выше, автоматически означает вызов для группы.

Ориентиры для первого дня:

- **порог = лучшему в штате** → правильный человек даёт жёлтый, неправильный красный.
  Это рабочая норма: 80 % при верном выборе, 16–30 % при неверном;
- **порог на 1 выше лучшего** → правильного выбора не существует, только меньшее зло.
  Так делают вызовы, которые игрок обязан провалить по сюжету;
- **порог на 2 ниже лучшего** → зелёный, автоуспех. Годится для обучения, но не должно
  быть нормой: без броска нет напряжения.

Помните про дневной множитель: день 2 умножает пороги на 1.15, день 3 — на 1.3,
день 4 — на 1.5, и результат округляется вверх. Порог 5 на четвёртом дне превращается
в 8 — одиночке это недоступно вовсе (потолок характеристики 7), так что вызов обязан
иметь `squadLimit` не меньше двух. Район на пороги не влияет: он задаёт только частоту
вызовов через `baseWeight`.

**Не гадайте — запустите `preview`.** Он покажет ровно то, что получит игрок:

```
=== m_pensioner_door  (Story, день 1, мест: 2)
    пороги: Интеллект 5 ★, Харизма 4, Сила 5, Боевая подготовка 4
  Горин              Сила 5/5 жёлт   Бой 4/4 жёлт   Хар 3/4 КРАСН  Инт 3/5 КРАСН →    42%
  Васнецова          Сила 3/5 КРАСН  Бой 3/4 КРАСН  Хар 3/4 КРАСН  Инт 5/5 жёлт  →    45%
  Лядов              Сила 4/5 КРАСН  Бой 4/4 жёлт   Хар 4/4 жёлт   Инт 3/5 КРАСН →    42%
  Горин + Васнецова  Сила 8/5 ЗЕЛ    Бой 7/4 ЗЕЛ    Хар 6/4 ЗЕЛ    Инт 8/5 ЗЕЛ   → АВТОУСПЕХ
  Горин + Лядов      Сила 9/5 ЗЕЛ    Бой 8/4 ЗЕЛ    Хар 7/4 ЗЕЛ    Инт 6/5 жёлт  →    92%
  Васнецова + Лядов  Сила 7/5 ЗЕЛ    Бой 7/4 ЗЕЛ    Хар 7/4 ЗЕЛ    Инт 8/5 ЗЕЛ   → АВТОУСПЕХ
```

Последняя строка — проверка на здравый смысл. Здесь видно и типичную ошибку: на этой миссии любая пара выбивает автоуспех, а любой
одиночка — сорок процентов. Значит порог поставлен «под одного», а слотов дано два, и
выбор подменяется правилом «бери двоих». Лечится либо `squadLimit: 1`, либо порогами,
поднятыми под пару. Если разница между составами мала — то же самое, только наоборот.

## 4. Варианты решения

Вмешательство по радио бывает **только у сюжетных вызовов** — треск радио должен означать,
что дело серьёзное. У филлеров вариантов нет.

Варианты пишутся в `content/raw/mission_events/<имя>.md`:

```markdown
## Вариант: Пройти мимо
id: pass_by
quality: good

Тихо пройти мимо существа, стараясь не привлекать внимание.

## Вариант: Забрать на исследование
id: capture
quality: bad
requires: сила 5
requirement_modifier: 3

Напасть на существо и забрать его с собой.
```

| Поле | Что делает |
|---|---|
| `id` | ключ. По нему связаны отчёт и последствия. Название можно править свободно, `id` — нет |
| `quality` | `good` \| `neutral` \| `bad`. Задаёт умолчания и проверяется на сборке |
| `requires` | порог, ниже которого вариант **закрыт**. Пусто — открыт всегда |
| `requirement_modifier` | надбавка к порогам вызова: +N к каждому. Не написан — берётся от `quality` |

### Что делает `quality`

| Тип | Надбавка по умолчанию | Множитель рисков |
|---|---|---|
| `good` | 0 | 1.0 |
| `neutral` | +1 | 1.0 |
| `bad` | +2 | 1.5 |

Написали число руками — оно сильнее умолчания. Но **сборка упадёт, если тип и цена
разошлись**: хороший вариант не может быть дороже плохого. Это не придирка — тип
существует ровно для того, чтобы игрок мог его вычислить по последствиям.

`quality` **не показывается игроку**. Он должен догадаться сам, сопоставив формулировку
с абзацами энциклопедии. Никаких «(рекомендуется)» в тексте варианта.

### Закрытые варианты

`requires` сравнивается с профилем **уже отправленной группы**. Отправил не тех — умные
решения закрыты, остаётся то, что есть. Игрок видит закрытый вариант неактивным с причиной:
«не хватает Сила 2». Это связывает два экрана: решение на отправке отзывается на радио.

**Хотя бы один вариант обязан быть без `requires`** — иначе слабой группе нечего нажать,
а таймер радио идёт. Сборка это проверяет.

Совет по расстановке: держите **всегда открытым нейтральный** вариант, а требования вешайте
на хороший (сообразить хитрость) и на плохой (хватит наглости полезть в драку). Тогда слабый
отряд получает пресный исход, а сильный — настоящую развилку. Если всегда открыт хороший,
слабая группа оказывается заперта в правильном выборе, и решение исчезает.

## 5. Последствия

### Шкалы

Четыре набора в `missions.json`: `scalesOnSuccess`, `scalesOnFailure`, `scalesOnMissedCall`
(не взяли трубку), `scalesOnExpiredMarker` (не отправили группу). Плюс `extraScales`
у варианта в `mission_events.json` — они складываются с исходом.

Положительное значение — рост шкалы. Для заражения и гласности рост это плохо, для
лояльности — хорошо.

### Риски

`injuryChance` и `deathChance` — базовые шансы **на каждого бойца**. Умножаются на риск
от совпадения профилей (`1 + (1 − совпадение) × 1.5`), на множители варианта и снаряжения,
и режутся при успехе: травма ×0.25, гибель ×0.1.

Ориентир: 0.2 травма и 0.05 гибель для сюжетного вызова. При полном совпадении это даёт
около 5 % травмы и 0.6 % гибели на человека — редко, но за смену кто-то возвращается раненым.

### Потолок последствий

```json
"tier": "Story",
"consequenceCap": "Injury"
```

Отвечает на вопрос «что здесь максимум может случиться»: `None`, `Injury`, `Death`.
По умолчанию берётся от уровня: сюжетный — гибель, филлер — травма.

**Это потолок, а не вероятность.** Числа рисков остаются, потолок обрезает их последним,
уже после всех множителей. Поэтому «в детском саду не умирают» нельзя случайно нарушить,
перекрутив баланс.

Вариант может **ужесточить** потолок, но не ослабить: «спрятаться в кладовке» безопасно
везде, но никакой выбор не сделает смертельным вызов, объявленный безопасным.

### Энциклопедия

У варианта в `mission_events.json`:

- `revealsPropertyId` — гарантированно раскрывает свойство существа. Работает **независимо
  от успеха**, лишь бы кто-то вернулся живым: провалили, но узнали — знание осталось.

Раньше здесь был ещё `appliesQuarantine`, закрывавший район. Состояний у районов больше
нет; чтобы вариант «оцепить квартал» что-то значил механически, задайте ему последствия
на шкалах через `extraScales`.

## 6. Отчёты

Отчёт пишется **на каждую пару «вариант × исход»**. Для вызова с тремя вариантами это
восемь файлов: три пары плюс пара на исход без вмешательства.

Связка живёт в `missions.json`, а не в самом отчёте — отчёт по схеме текстового движка
не знает ни о миссии, ни о варианте:

```json
"reports": {
  "":        { "success": "report_x_plain_success",   "failure": "report_x_plain_failure" },
  "pass_by": { "success": "report_x_pass_by_success", "failure": "report_x_pass_by_failure" }
}
```

Один и тот же id можно указать дважды — так сделано в чёрной плесени, где «Уксус и ковры»
служит и исходом без вмешательства.

Ключ `""` обязателен: игрок мог не успеть взять радио.

## 7. Уровни вызовов

| | Сюжетный (`Story`) | Филлерный (`Filler`) |
|---|---|---|
| Гибель | возможна | исключена |
| Вмешательство по радио | есть | не бывает |
| Роль в смене | развилки и сюжет | ритм, расход ресурса группы |

Умолчание — `Filler`: забытое поле не должно молча включать смерти.

## 8. Чек-лист перед сдачей

- [ ] `preview` показывает 70–85 % при правильном выборе и заметно меньше при неправильном
- [ ] «весь штат» не лучше правильной пары — иначе решение подменяется отправкой всех
- [ ] главная характеристика назначена и входит в пороги
- [ ] хотя бы один вариант открыт всегда
- [ ] тип диалога и надбавка не спорят друг с другом
- [ ] у каждой пары «вариант × исход» есть отчёт, включая `""`
- [ ] если по смыслу тут нельзя погибнуть — стоит `consequenceCap`
- [ ] `check` молчит

## 9. Частые ошибки

**Пороги от суммы, а не от лучшего.** Самая частая: автор считает «трое по три = девять»
и ставит порог 8. Сравнивается лучший, так что порог 8 недостижим ничем.

**Забыли множитель дня.** Порог 6 на четвёртом дне превращается в 9. Смотрите `preview`
именно для того дня, на который ставите вызов.

**Все варианты с требованиями.** Сборка упадёт, но лучше не доводить: подумайте, что
делает игрок, приехавший неподходящим составом.

**Хороший вариант дороже плохого.** Тоже упадёт на сборке. Если так вышло по смыслу —
скорее всего, вы поменяли местами `quality`, а не нашли исключение из правила.

**Проза в `data`.** Ни одной строки текста в JSON быть не должно: только id. Если хочется
написать туда фразу — значит, для неё нет записи в `content/raw`, и её надо завести.

**Отчёт без пары.** Написали текст на успех, забыли на провал. `check` поймает, но легче
писать их сразу парами.
