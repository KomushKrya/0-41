# Текстовый движок и миссии

Всё, что нужно автору: как устроены тексты, как размечаются, как собираются, как из них
и чисел складывается миссия и как это выводится на экран.

Смежное: все поля JSON — `kontur-core/docs/CONTENT_SCHEMA.md`, справочник по коду ядра —
`docs/ядро-api.md`, правила игры целиком — `README.md`.

---

## 1. Как это устроено

```
   content/raw/<локаль>/**/*.md
        │  python content/engine/converter/build.py
        ▼
   content/localisation/<локаль>/**/<тип>.json
        │  автозагрузка Content
        ▼
   ContentEntry { Chunks[], Properties[], Options[], ... }
        │  ContentTextBox: фильтр по флагам GameState
        ▼
   Render() у наследника
```

**Текст не пишется в сцене и не приходит в событии — он берётся по id.**

**Кусок (chunk) — единица текста:** абзац, отделённый пустой строкой. Для нижнего текста
один кусок = один клик, для энциклопедии — один абзац статьи.

**Базовый класс ничего не рисует.** Он достаёт запись по id и выбрасывает условные
абзацы, которые игра ещё не открыла. Вёрстка и пагинация — у наследника.

---

## 2. Раскладка

```
content/raw/
  _system/        шаблоны, реестр id, этот файл — в сборку не идёт
  ru/             missions/ cutscenes/ creatures/ equipment/ shift_notes/ UI/
```

Сборка по одной локали: `--locale ru` читает `content/raw/ru/`, пишет в
`content/localisation/ru/`. Новый язык — папка рядом с `ru/` той же структуры.

`_system/ids_registry.md` генерируется конвертером, руками не правится.

## 3. Типы записей

Пути от корня локали.

| Тип | Папка | Особенности |
|---|---|---|
| `mission_id` | `missions/mission_ids/chapter_N/shift_N.md` | Таблица «id — название» на смену. Своего id у файла нет. |
| `call` | `missions/calls/…` | `mission_type: radio\|filler`, `requires`. Шапка `%% call_meta %%`, дальше абзацы, ключевые слова `==…==`. |
| `radio` | `missions/radio/…` | Вводная, затем `## Вариант: <название>` с `id` и `requires`. Минимум один вариант. |
| `report` | `missions/reports/…/<миссия>/` | `outcome`. |
| `cutscene` | `cutscenes/` | Нижний текст: кусок ≤150 символов, иначе не влезет в две строки. |
| `creature` | `creatures/` | `name`, 4 абзаца: первый открыт, остальные под `%% reveal %%`, их id = `properties`. |
| `shift_note` | `shift_notes/` | `day`. |
| `equipment` | `equipment/` | `name`. Числа — в `data/equipment.json` под тем же id. |
| `perk` | `UI/hover_footnote/perks/` | `name`. Числа — в `data/abilities.json`. |
| `characteristic` | `UI/hover_footnote/characteristics/` | `name` — подпись в досье, id как в ядре. |
| `equipment_kind` | `UI/hover_footnote/equipment_kinds/` | `consumable`, `standard`, `story`. |
| `scale` | `UI/hover_footnote/scales/` | `infection`, `publicity`, `loyalty`. |

Вложенность внутри папки типа свободная. У четырёх папок под `missions/` она
договорная — `chapter_<N>/shift_<N>/`, чтобы тексты одной миссии лежали на одной глубине.

## 4. Фронтматтер и теги

`id` уникален по всему `content/raw`; у `perk`, `characteristic`, `equipment` совпадает
с id в геймплейных данных. `status: draft|ready` — черновики в обычную сборку не идут.
`requirements` — флаги появления записи, движок их только передаёт. `properties` — id
условных блоков, реально работает у `creature`.

Схема намеренно узкая: скаляры и простые списки. Что не укладывается — ошибка сборки,
а не молчаливый пропуск.

| Тег | Что делает |
|---|---|
| `**слово**` | Жирный: подписи и ярлыки, всё, что не речь. |
| `==слово==` | Ключевое слово вызова, красится `#d27253`. См. раздел 5. |
| `[[тип:id]]` | Кросс-ссылка. Битая роняет сборку, **в рантайме не разворачивается** — в показываемый текст не ставим. |
| `%% reveal: <id> %% … %% /reveal %%` | Условный блок, показывать или нет решает игра. |
| `%% call_meta: <текст> %%` | Шапка звонка, только у `call`. Едет своим куском, чтобы интерфейс показал её отдельно от реплик. Скобки добавляет интерфейс. |
| `{{имя}}` | Число из геймплейных данных: `+{{bonus.strength}} к силе`. Имена собираются в `variables`, подставляет игра. |
| `%% dev: … %%`, `%% dev %% … %% /dev %%` | Заметка для разработчиков, вырезается до разбора. Незакрытый тег — ошибка. |

`%%` Обсидиан прячет в режиме чтения, `==` и `**` показывает — потому подсветка и жирный
сделаны markdown-ом, а служебное комментариями.

## 5. Ключевые слова вызовов

```markdown
У меня ==дочка маленькая==, не хочу, чтобы она чем-то там ==надышалась==.
```

**Тег только красит.** Какую характеристику слово подсказывает, нигде не пишется —
сопоставить зацепку с навыком и есть работа игрока. Ставится **только в `call`**,
два-три слова на вызов.

Правила и таблица «слово — характеристика» — `_system/keywords.md`.

## 6. Из чего состоит миссия

```
   data/missions.json          ← числа: пороги, риски, шкалы, тайминги
   data/mission_events.json    ← числа вариантов: риски, последствия, карантин
        │  ссылаются по id
        ▼
   missions/mission_ids/chapter_N/shift_N.md  ← название миссии
   missions/calls/…/<имя>.md                  ← что говорят в трубку
   missions/radio/…/<имя>.md                  ← что видят на месте + варианты
   missions/reports/…/<имя>/*.md              ← отчёты: вариант × исход
```

**Всё, что пишется словами, — в `content/raw`; всё, что крутится числами, — в `data`.**
Без исключений: в тексте варианта нет ни одного числа, только формулировка, ключ и
список проверяемых характеристик.

**Связь текстов одной миссии — поле `mission_id`** в `call`, `radio` и `report`: ссылка
на строку реестра. Пустое или битое роняет сборку. Название миссии живёт только там,
а id совпадает с id миссии в `data/missions.json` — один ключ на обе стороны.

### Команды

```bash
python content/engine/tools/mission.py new                   # завести миссию целиком
python content/engine/converter/build.py --include-drafts    # собрать тексты
python content/engine/tools/mission.py preview m_моя_миссия  # во что превратились пороги
python content/engine/tools/mission.py check                 # сверить всё со всем
```

Порядок такой: завели → написали тексты → собрали → посмотрели → проверили. `check`
объясняет проблемы словами и отличает «текста нет» от «текст есть, но забыли собрать».

### Уровни вызовов

| | Сюжетный (`Story`) | Филлерный (`Filler`) |
|---|---|---|
| Гибель | возможна | исключена |
| Вмешательство по радио | есть | не бывает |
| Роль в смене | развилки и сюжет | ритм, расход ресурса группы |

Умолчание — `Filler`: забытое поле не должно молча включать смерти.

## 7. Пороги характеристик

У вызова нет общей «сложности», есть пороги по отдельным характеристикам:

```json
"requirements": { "intellect": 5, "combat": 4 },
"primaryStat": "intellect"
```

**Сравнивается лучший в группе, а не сумма.** Порог «Интеллект 5» закрывает тот, у кого
интеллект не ниже пяти. Трое невнимательных не заменяют одного глазастого — поэтому
игрок собирает состав под требования, а не отправляет всех.

**Главная характеристика весит вдвое.** Основной рычаг: не нужно задирать числа, чтобы
показать, что вызов «про сообразительность» — достаточно назначить интеллект главным.
Главная обязана входить в пороги, иначе загрузка упадёт.

| Ступень | Условие | Вклад в процент |
|---|---|---|
| Зелёная | превышение на 2 и больше | полный |
| Жёлтая | ровно дотянул или +1 | 0.8 |
| Красная | недобор | падает **втрое за каждое** недостающее очко |

Все зелёные — успех без броска. Иначе процент это взвешенное среднее вкладов, и по нему
бросается кубик. Красный не запрещает отправку: иногда приходится ехать теми, кто остался.

### Сколько ставить

| Кто | Сила | Боевая | Ловкость | Харизма | Интеллект |
|---|---|---|---|---|---|
| Горин А. П. | 5 | 4 | 3 | 3 | 3 |
| Васнецова И. С. | 3 | 3 | 4 | 3 | 5 |
| Лядов М. М. | 4 | 4 | 3 | 4 | 3 |
| **Лучший в стартовом штате** | **5** | **4** | **4** | **4** | **5** |
| Шубин Р. К. (с дня 2) | 4 | 4 | 3 | 3 | 4 |
| Теплова Н. В. (с дня 2) | 3 | 3 | 5 | 3 | 5 |
| Карнаух В. Б. (с дня 3) | 6 | 5 | 3 | 4 | 4 |
| Прус Е. Д. (с дня 3) | 4 | 4 | 5 | 4 | 6 |
| Жилин С. А. (с дня 4) | 6 | 6 | 4 | 6 | 5 |

- **порог = лучшему в штате** → правильный человек даёт жёлтый, неправильный красный.
  Рабочая норма: 80 % при верном выборе, 16–30 % при неверном;
- **на 1 выше лучшего** → правильного выбора не существует, только меньшее зло. Так
  делают вызовы, которые игрок обязан провалить по сюжету;
- **на 2 ниже лучшего** → зелёный, автоуспех. Для обучения, но не нормой.

День 2 умножает пороги на 1.15, день 3 — на 1.3, день 4 — на 1.5, заражённый район ещё
на 1.2. Порог 5 на четвёртом дне в заражённой зоне превращается в 9 — за пределами штата.

**Не гадайте — запустите `preview`.** Последняя строка вывода, «весь штат», — проверка на
здравый смысл: если она заметно лучше правильной пары, решение подменяется отправкой всех.

## 8. Варианты решения

Вмешательство по радио бывает **только у сюжетных вызовов** — треск радио должен
означать, что дело серьёзное.

```markdown
## Вариант: Пройти мимо
id: pass_by

Тихо пройти мимо существа, стараясь не привлекать внимание.

## Вариант: Забрать на исследование
id: capture
requires: сила, боевая подготовка

Напасть на существо и забрать его с собой.
```

`id` — ключ: по нему связаны отчёт и последствия. Название правится свободно, `id` — нет.

`requires` — перечисление характеристик через запятую, **без чисел**. Пять допустимых:
**сила**, **боевая подготовка**, **ловкость**, **харизма**, **интеллект**. Незнакомое
название и любое число роняют сборку, чтобы опечатка не стала «проверки нет».

Порога в тексте нет намеренно: порог — требование миссии по той же характеристике из
`data/missions.json`. Текст отвечает «что проверяем», данные — «насколько трудно».
Иначе одно число пришлось бы держать синхронным в двух местах.

**Проверка ничего не запирает.** Вариант доступен всегда: не хватило характеристик —
падает шанс, а не пропадает кнопка. Игрок с неподходящей группой не упирается в серую
кнопку, а рискует и узнаёт цену выбора по отчёту. Вариант без `requires` — тот, где
проверять нечего: исход у него один и предрешён.

У филлерного вызова `requires` стоит во фронтматтере и обязан назвать минимум две
характеристики: это единственная проверка миссии.

**Тип варианта (`quality`) в текст не попадает вовсе** — он в `data/mission_events.json`.
Подсказок о правильности в интерфейсе быть не должно: игрок сопоставляет формулировку
с абзацами энциклопедии сам.

## 9. Последствия

**Шкалы.** Четыре набора в `missions.json`: `scalesOnSuccess`, `scalesOnFailure`,
`scalesOnMissedCall` (не взяли трубку), `scalesOnExpiredMarker` (не отправили группу).
Плюс `extraScales` у варианта — складывается с исходом. Положительное значение это рост:
для заражения и гласности плохо, для лояльности хорошо.

**Риски.** `injuryChance` и `deathChance` — базовые шансы **на каждого бойца**.
Умножаются на риск от совпадения профилей (`1 + (1 − совпадение) × 1.5`), на множители
варианта и снаряжения, режутся при успехе: травма ×0.25, гибель ×0.1. Ориентир для
сюжетного вызова — 0.2 и 0.05: при полном совпадении это около 5 % травмы и 0.6 % гибели.

**Потолок последствий** (`consequenceCap`: `None`, `Injury`, `Death`) отвечает на вопрос
«что здесь максимум может случиться». По умолчанию берётся от уровня: сюжетный — гибель,
филлер — травма. Это потолок, а не вероятность: он обрезает риски последним, уже после
всех множителей, поэтому «в детском саду не умирают» нельзя нарушить, перекрутив баланс.
Вариант может ужесточить потолок, но не ослабить.

**Карантин и энциклопедия.** У варианта: `appliesQuarantine` переводит район в карантин,
вызовов оттуда станет меньше; `revealsPropertyId` гарантированно раскрывает свойство
существа — **независимо от успеха**, лишь бы кто-то вернулся живым: провалили, но узнали.

## 10. Отчёты

Отчёт пишется **на каждую пару «вариант × исход»**. Для вызова с тремя вариантами это
восемь файлов: три пары плюс пара на исход без вмешательства.

Связка живёт в `missions.json`, а не в отчёте — отчёт не знает ни о миссии, ни о варианте:

```json
"reports": {
  "":        { "success": "report_x_plain_success",   "failure": "report_x_plain_failure" },
  "pass_by": { "success": "report_x_pass_by_success", "failure": "report_x_pass_by_failure" }
}
```

Ключ `""` обязателен: игрок мог не успеть взять радио. Один и тот же id можно указать
дважды — так сделано в чёрной плесени, где «Уксус и ковры» служит и исходом без
вмешательства, и у вариантов без проверки, где исход один на любой бросок.

## 11. Сборка

```bash
python content/engine/converter/build.py                    # только status: ready
python content/engine/converter/build.py --include-drafts   # вместе с черновиками
python content/engine/converter/build.py --locale en        # другая локаль
```

Зависимостей нет. Конвертер собирает **все** ошибки и печатает списком, а не падает
на первой. Заодно перегенерирует `ids_registry.md`.

Что проверяется: уникальность id; тип против папки; неизвестная папка; не-UTF-8;
незакрытые `%% dev %%` и `%% reveal %%`; `properties` против фактических блоков; битые
`[[тип:id]]`; пустой или несуществующий `mission_id`; формат `requires` и незнакомые
характеристики; `id` варианта и его уникальность в файле; `call_meta` не у своего типа.
Кусок длиннее 150 символов у `cutscene` — предупреждение, не ошибка.

## 12. Вывод текста: `ContentTextBox`

`scripts/ui/ContentTextBox.cs`, пример наследника — `scripts/ui/EncyclopediaTextBox.cs`.

```csharp
public partial class ReportBox : ContentTextBox
{
    [Export] public NodePath LabelPath { get; set; } = new("Label");
    private RichTextLabel _label;

    public override void _Ready()
    {
        _label = GetNode<RichTextLabel>(LabelPath);   // до base: тот сразу вызовет Render()
        base._Ready();
    }

    protected override void Render()
    {
        var text = new StringBuilder();
        foreach (ContentChunk chunk in Chunks) { text.Append(chunk.ToBbcode()).Append("\n\n"); }
        _label.Text = text.ToString().TrimEnd('\n');
    }
}
```

Выставить `ContentId` в инспекторе — бокс наполнится сам; либо `Open(id)` по событию.

**В инспекторе:** `ContentId`, `OpenOnReady` (грузить сразу), `RevealEverything`
(показать все условные абзацы — только для превью вёрстки), `RefreshOnReveal`
(перечитываться при смене флага).

**Наследнику доступно:** `Chunks` — видимые куски, `Entry` — запись целиком,
`CallMeta` — шапка звонка без скобок, `IsLoaded`, `Open(id)`, `Refresh()`,
`IsChunkVisible(chunk)`.

**Переопределяется:** `Render()` (обязательный), `IsRevealed(propertyId)` — если флаги
живут не в `GameState`, `OnMissingContent(id)` — если ненайденный id штатная ситуация.

`Render()` зовётся и **с пустым списком** — наследник обязан уметь себя чистить.

### Условные абзацы

Скрытые куски просто не попадают в `Chunks`. Вопрос задаётся ядру в два шага: сюжетный
флаг с именем, равным id свойства, и раскрытия энциклопедии — свойство могло открыться
отчётом с выезда.

```csharp
KonturRuntime.Get(this).Simulation.SetFlag("property_mimic_routine");
```

Дальше ничего не нужно: ядро публикует `FlagChanged`, боксы с `RefreshOnReveal`
перечитываются сами. Чтобы показать, что абзац есть, но закрыт, иди по `Entry.Chunks`
и спрашивай `IsChunkVisible` — так сделано в энциклопедии («ДАННЫЕ НЕ ПОДТВЕРЖДЕНЫ»).

### Подсветка

Кусок несёт `Spans` — отрезки, где у ключевых слов взведён `Highlight`, у подписей
`Bold`. Собирать руками не надо: `chunk.ToBbcode()` даёт готовый BBCode и экранирует
квадратные скобки самого текста, так что `[1985]` в реплике не разберётся как разметка.

Отрезки, а не позиции, — потому что подстановка `{{имя}}` меняет длину, и смещения
после неё уехали бы.

### Варианты в интерфейсе

У `radio` варианты в `Entry.Options`: `Id`, `Name`, `Requirements`, свои `Chunks`.
Отвечать ядру нужно `Id`, подписывать кнопку — `Name`. Порядок совпадает с порядком
в событии `RadioTriggered`.

## 13. Чек-лист перед сдачей

- [ ] `preview` даёт 70–85 % при правильном выборе и заметно меньше при неправильном
- [ ] «весь штат» не лучше правильной пары
- [ ] главная характеристика назначена и входит в пороги
- [ ] у каждой пары «вариант × исход» есть отчёт, включая `""`
- [ ] если по смыслу тут нельзя погибнуть — стоит `consequenceCap`
- [ ] `check` молчит

## 14. Грабли

**Пороги от суммы, а не от лучшего.** Самая частая: «трое по три = девять», ставят
порог 8. Сравнивается лучший, так что порог 8 недостижим ничем.

**Забыли множитель дня.** Порог 6 на четвёртом дне превращается в 9. Смотрите `preview`
именно для того дня, на который ставите вызов.

**Проза в `data`.** Ни одной строки текста в JSON: только id. Хочется написать туда
фразу — значит, для неё нет записи в `content/raw`, и её надо завести.

**Отчёт без пары.** Написали на успех, забыли на провал. `check` поймает, но легче
писать сразу парами.

**Проверка по «чужой» характеристике.** Вариант проверяет то, чего нет в порогах
миссии — порог подставится нулевой, и проверка станет бесплатной. Ловится на загрузке ядра.

**BBCode.** `RichTextLabel` с `BbcodeEnabled` разберёт любую квадратную скобку как
разметку. Либо выключай bbcode, либо зови `ToBbcode()`.

**`[[тип:id]]` не разворачивается** — игрок увидит ссылку буквально.

**Пустой `Chunks` — нормально.** Запись не нашлась, все абзацы закрыты, `Open("")`.

**Подписки.** Базовый класс снимает свои в `_ExitTree()`; подписался на своё — снимай
сам и зови `base._ExitTree()`.

**Автозагрузки.** Нужны `Content` и `Kontur`. Без них бокс не падает: предупреждение
в Output и пустой экран.

**Опечатка в id падает на старте** — ядро сверяет ссылки с текстами через `ITextCatalog`:

```
Миссия 'm_pensioner_door': нет записи report с id 'report_pensioner_door_pass_by_succes'
Вмешательство 'radio_black_mold': вариант 'reagant' есть в данных, но не в тексте
```

## Открытые вопросы

- Как `%% reveal %%` доходит до Godot: JSON с условием или решение целиком за игрой?
- `properties` осмысленно только у `creature`; на остальных типах это пустой задел.
