# Схема фронтматтера и кастомных тегов (черновик)

Статус: черновик для ревизии, как только начнётся написание конвертера
(`content/engine/converter`). Ничего здесь ещё не парсится реальным кодом — это
только договорённость об ожидаемом формате `.md`, чтобы контент и конвертер писались
навстречу друг другу.

## Общие поля фронтматтера (обязательны для всех типов)

```yaml
id: incident_school_mimic_01   # уникален в пределах всего content/raw, не только папки
type: incident                 # incident | radio | creature | shift_note | report | story
status: draft                  # draft | ready — конвертер по умолчанию пропускает draft
```

`id` — единственное, что гарантирует движок (по нему `Content`-автолоад отдаёт данные в
игру). Уникальность в рамках всего дерева `raw/`, а не только одной подпапки — иначе
конвертер должен будет молча выбирать один из дублей, что хуже, чем упасть с ошибкой на
билде. Пока это отслеживается вручную в [`_system/ids_registry.md`](../ids_registry.md) —
каждый новый `id` нужно туда дописывать.

`status` — черновики (`draft`) не должны попадать в билд, пока автор явно не пометит текст
`ready`. Позволяет держать недописанные вызовы/диалоги в репозитории, не ломая сборку.

## Поля по типам (черновик, дополнять при реализации)

### incident
```yaml
id: incident_...
type: incident
requirements: { strength: 5, endurance: 6 }
creature_id: creature_mimic       # опционально
radio_id: radio_...               # опционально, если миссия требует вмешательства
report_id: report_...
```
Тело файла — текст, который слышит игрок при ответе на звонок.

### radio
```yaml
id: radio_...
incident_id: incident_...
```
Тело — вводная («что видят сотрудники»), затем три варианта решения как секции
`## Вариант: <название>` с блоком метаданных сразу после заголовка:
```
## Вариант: Притвориться учениками
requirement_modifier: -2
canon: correct   # correct | wrong | trap
```

### creature
```yaml
id: creature_...
name: Мимик
```
Тело — 4 абзаца. Первый всегда виден игроку, остальные три обёрнуты кастомным тегом
раскрытия по свойству:
```
%% reveal: property_mimic_sound %%
Абзац, который появится в энциклопедии только после того, как это свойство
проявилось на вызове.
%% /reveal %%
```

### shift_note
```yaml
id: shift_note_day_1
day: 1
```

### report
```yaml
id: report_...
incident_id: incident_...
outcome: success   # success | fail
creature_id: creature_...
```

### story
```yaml
id: story_day_1_to_2
```

## Кастомные inline-теги

- `[[type:id]]` — перекрёстная ссылка на другой контент (например, из отчёта на
  существо). Конвертер должен на билде проверять, что цель существует, и падать с
  понятной ошибкой, если нет — это дешевле, чем ловить битые ссылки в рантайме Godot.
- `%% reveal: <property_id> %% ... %% /reveal %%` — блок, видимый только после того,
  как игра сообщит движку, что свойство раскрыто. Сам факт "раскрыто ли" — не забота
  текстового движка, он только выдаёт список абзацев с пометкой, какие условны.

## Открытые вопросы (перенесены из README.md, п.16, и требуют решения при реализации)

- Как именно `%% reveal %%` дойдёт до Godot: конвертер отдаёт JSON с массивом
  `{ text, reveal_condition | null }`, а решение "показывать или нет" принимает игра —
  или конвертер должен что-то знать о состоянии игрока? (Предполагаемый ответ: первое —
  движок только маркирует условность, ничего не решает, но explicitly не зафиксировано.)
- Формат `requirement_modifier` в `radio` — абсолютное число, процент, или ссылка на
  конкретную характеристику (может отличаться по миссиям)?
- Нужна ли валидация уникальности `id` прямо в конвертере при билде, или отдельным
  линтером до него? Пока — ручной реестр в `_system/ids_registry.md`, но это не
  проверка, а просто памятка; настоящая защита от коллизий появится только когда
  конвертер начнёт её делать сам.
